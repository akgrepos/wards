# Notes for Claude

## Who this is for
The owner, a physician, is the only user. No coding experience: explain steps plainly and avoid jargon.

## How to work here
- **Don't build anything the owner hasn't asked for.** Propose options, wait for a decision, then build only what was agreed. Answering a question is not permission to build.
- **Main chat and side sessions.** A chat the owner opens directly is the **Main** chat: follow the `wards-main` skill in the owner's Claude settings (it renames the chat to "Main" and runs the project as the organizer). Main delegates all building, card writing and mock-ups to side sessions it starts with a brief, keeps branches and sessions clean, and closes sessions once their work is merged and live. The owner works inside each side session's own chat. A session started with a brief is a side session: do its task, not Main's job.
- **At most two side sessions at a time**, plus the Main chat (owner, 2026-10-21, to conserve usage; was three, then one, now two). Finish and close one before starting a third. Two sessions never edit the same files; a mock-up-only session that doesn't touch the repo doesn't count.
- **Conserve usage** (owner, 2026-10-21):
  - *Cheapest model that does the job well* (owner: Opus only where it's needed). **Sonnet is the default** for side sessions and subagents: building features and fixes, mock-ups, notes and STATUS changes, preview testing, design-system checks, merging. **Haiku** for simple steps: finding files, listing, checking that links load, gathering screenshots, routine status checks. **Opus only** for clinical card writing, dose and claim verification, the independent clinical reviewer, and the independent design review of a brand-new layout or mock-up (Sonnet builds it; small visual fixes don't need it), where accuracy and taste matter most. A session that hits something genuinely hard may hand that one piece to a more capable subagent.
  - *Read narrowly.* Read the DECISIONS rows a brief names, not the whole file; read only the cards and data you change.
  - *Test in proportion* (rules below): screenshots only of the screens that changed. Wait for checks with one `gh pr checks <n> --watch` instead of checking repeatedly.
  - *Few rounds.* Mock-ups offer two or three clear options in one round; ask the owner one combined question pop-up instead of several in a row.
  - *Split long sessions.* A card-writing session drafts, verifies (Sonnet drafts; an Opus subagent verifies doses and care-changing claims) and pushes its branch, then opens a draft PR with the full detail (guidelines found, dose sources, review notes). Main starts a fresh Sonnet "ship" session that picks up the draft PR for preview testing, screenshots, version, changelog and merge. Don't let one session carry everything.
  - *Extras only where they matter.* A Rapids page, a focused pathway or an ECG figure is added to a card only for a true emergency, a true sequence of decisions or a pattern recognized by sight. The brief names the minimum and the session asks one combined pop-up; MDCalc links always stay.
  - *One card per session, fresh each time.* A card-writing session covers one card (the owner can still review three on the phone as a batch). Don't carry a session across cards; its conversation grows and every step re-reads it.
  - *Lower effort for non-clinical sessions.* Ship, notes, fixes and mock-up builds start at low or medium reasoning effort (`effort` on `start_session`); clinical writing and dose verification keep the default.
  - *Light notes and screenshots.* Read the named rows and files only. Screenshots: few and small (scale down; read page text where it answers the question).
  - *Ask up front, then work straight through.* A session asks all its owner questions in one combined pop-up at the start, so it isn't left idle for hours mid-task (an idle session pays to re-read its whole conversation when it resumes). Main does the same when briefing.
  - *Short notes going forward.* A new DECISIONS row is at most about 700 characters (what, why, version); the detail (guidelines found, dose sources, review log) lives in the PR description and the private review log, not in DECISIONS or STATUS.
  - *Narrow research reads.* In AMBOSS and guideline pages, read the relevant section and the reference list with a page-text limit, not whole pages. Save a batch's newest-guideline list once, privately in `~/Documents/Wards-reference/`, so the later review pass reuses it.
  - *Pace the week.* The weekly budget is about 14% a day. Main reads `get_usage` at the start of each day and, if the weekly percentage is ahead of that pace or the 5-hour limit is above about 70%, starts nothing big and tells the owner.
  - *Close promptly.* Finished sessions are archived as soon as their work is merged and live.
- **One branch and pull request per task.** Never commit to `main` (it's protected). Branch names: `setup/…`, `feature/…`, `fix/…`, `content/…`. Open the PR with a plain-language summary.
- **Merge it yourself** with `gh pr merge --rebase` (the only method allowed) once the checks pass and testing below is done. Branches delete themselves. Never merge with a failing check. The owner reviews by using the app and asks for changes in chat.
- **Test in proportion to the change, with as few screenshots as possible** (owner, 2026-10-24). The owner works on the Mac. **Two tiers.** Tier 1, Claude: build, run the checks, then, for visual changes, look at the local preview before merging (see "Prototype first" below); for plain card or text edits and deploy, offline or update changes, confirm the live update in Safari in the iOS Simulator (rules in "Testing on the Mac" below). Look at the screen only when the change is visually new (see "Visible change"). Read page text and the build output where they answer the question; `npm run sim-check` is the cheap way to look at a screen. Tier 2, the owner: confirms on their iPhone after the deploy (tap Reload on the "Update Ready" banner) and is the main visual review. The Simulator cannot fully reproduce a real finger, the on-screen keyboard or the installed-app behavior, so reports say what was checked and what only the phone can confirm.
  - *One-call Simulator check:* `npm run sim-check` (README "Workflow scripts") reports the version shown versus `origin/main`, confirms expected text, and with `--shots` saves scaled-down light and dark shots outside the repo; tapping stays manual.
  - *Awaiting iPhone confirmation (owner, 2026-10-23):* every visible PR adds a line to `docs/REVIEW-QUEUE.md` "Awaiting iPhone confirmation" (version, what to tap, what should happen). Main clears a line when the owner confirms. For touch, scroll, keyboard or install behavior, the session says "confirm before the next change in this area" and Main does not start another change there until it is confirmed.
  - *Plain card or text edit (existing components only):* no screenshots. Confirm in the Simulator that the app updates and the card opens (Simulator screenshot at most one, scaled down, only if the page text cannot answer). The owner's iPhone check is the visual review; add its line to REVIEW-QUEUE.
  - *New component, table, pathway, Rapids page, figure or layout change:* one representative screen per kind of page, light and dark, scaled down (two or three images in total). Rapids changes also get one look in normal and one in Timed Mode. No Text Size checks (the owner will report any that break). Screenshots go in the PR description and are not committed to the repo (no `docs/screenshots/` folders; delete any left over). Bump the version in `src/version.ts` (`YYYY.MM.DD`, `.2` for a second release that day) and add a plain-language `CHANGELOG.md` entry; a test enforces that the two match.
  - *Behind-the-scenes change (build, security, tools):* a quick check that the app opens, works offline and still offers updates. No screenshots or version bump.
  - *Notes only, or a Dependabot PR with nothing visible:* the automatic checks are enough. Read a Dependabot PR's changes before merging.
- **Workflow scripts (Node):** use the one-call scripts (`npm run status`, `npm run wait-live`, `npm run tidy`, `npm run sim-check`, `npm run release`, `npm run card:new`) instead of repeating those steps by hand; see README "Workflow scripts".
- **Record decisions** in `docs/DECISIONS.md` (date, what, why) and keep `docs/STATUS.md` a short current snapshot. Move items out of "Open questions" when settled.
- `main` publishes to the live app automatically; the owner gets it after tapping Reload on the "Update Ready" banner.

- **End of a chat:** when the owner says to wrap up (or is done for the day), follow the `wards-wrap-up` skill in the owner's Claude settings: finish or park work, stop servers, clean Git and files, update STATUS/DECISIONS/memory, and leave a "Start here next time" handoff.

## Shell habit
Never write files or run scripts with heredocs (`cat > file <<'EOF'`, `python - <<'EOF'`): they can hang waiting for input and leave a stuck background task, which blocks archiving the session. Use the Write and Edit tools for files, run scripts from files (`node script.mjs`), and leave no background task running at the end of a turn.

## Prototype first, test before merging (owner, 2026-10-24)
- **Visual or layout ideas are prototyped in the real app, not as separate mock-ups.** A session (only when the owner asks) builds the change on a branch with the app's real components, builds it (`npm run build`, then `npm run preview`, so it behaves like the live app; dev mode skips the offline parts) and looks at it in Safari in the Simulator, which reaches the Mac at localhost. No deploy, merge or version bump to look at it. Two options go behind a temporary switch in the same prototype. Open `http://localhost:4173/wards/`; start the server with `npm run preview -- --host --strictPort` (a busy port then fails instead of silently moving) and stop it before the session ends, leaving nothing in the background. The app's service worker can keep showing an old build: before each look tap Reload on "Update Ready" or clear the site data in Simulator Safari, and confirm the expected text. The owner can open the preview in Safari on the iPhone over home Wi-Fi (`http://<mac-ip>:4173/wards/`); it is public content only, and on the phone only layout can be judged (no service worker there, so no offline or update behavior). `npm run sim-check` compares with the live site and is not valid on the preview: read page text. Mark any temporary switch with a `// PROTOTYPE` comment and remove it all before the PR (`grep -rn PROTOTYPE src` must be empty). A rejected prototype's branch is deleted; an approved one is already built. A prototype counts as a side session.
- **First-round structure options are sketched in the app too** (owner, 2026-10-24): several throwaway options in one preview, switchable by URL (`?home=1`, `?home=2`), using the real components, tokens and data; fake or empty behavior, no tests or polish; anything needing new storage or a feature is a one-line label, not built. All switch code is marked `// PROTOTYPE`. The sketch branch is never merged as is: the chosen option is built properly by a fresh session and the rest is deleted.
- **Mock-ups** (Artifacts) only for ideas the app cannot show yet (a new data type or a brand-new component).
- **Test once, before merging.** Visual changes are checked in the local preview first. After the deploy a session only confirms the live version (`npm run wait-live`); the owner's iPhone is the check of the live app. Use the live-site Simulator check below only when the live site itself matters (deploy, offline, update).

## Hard rules
- No patient information (PHI) anywhere: repo, app, pull requests or commit messages. The site and repo are public.
- Nothing sensitive or institution-internal (internal protocols, phone or pager numbers).
- **Stay anonymous.** Never put the owner's name, email or computer name in files, commits or PRs; refer to them as "the owner". Commits must be authored as `akgrepos <338781722+akgrepos@users.noreply.github.com>` (this repo's git config); a check rejects any other author.
- **Clinical content:** Claude writes it, evidence-based (full rules in DECISIONS.md, "Card-writing process" 2026-10-19 and "Sources, updated"):
  - The reference handbook is the starting outline: it decides what a card covers and how it's organized, including practical bedside details, in its terse clinical register. It is a guide only: never copy, closely paraphrase or reproduce its text, tables or structure verbatim; never name or cite it.
  - AMBOSS is the main drafting knowledge base; its reference lists supply the primary citations (a paywalled primary source may be cited on AMBOSS's word). Use it in the owner's own Chrome (Claude in Chrome, new window), where the sign-in lasts, in **Clinical care mode** (not Learning mode; owner, 2026-10-21).
  - **Newest-guideline search first:** before drafting or updating any card, search independently for the newest final guidelines and consensus statements (society websites, the guideline journals, PubMed for the last 24 months); don't rely on AMBOSS, the handbook or built-in knowledge for this. The review log lists the guidelines found with dates. The independent reviewer's repeat of this search moves to the later review pass (DECISIONS 2026-10-20 "Newest-guideline search before drafting", changed 2026-10-21).
  - Cite the primary guideline or study (US first, newest final edition; drafts aren't cited). Common clinical practice may go uncited with the stethoscope marker. AMBOSS itself only as a last resort (green check, hidden source, tell the owner each time).
  - Verify **every dose, number and threshold, and every claim that would change care** against the guideline full text, the FDA label and AMBOSS; routine sentences get one careful pass (see "Conserve usage" for who verifies). OpenEvidence is a last resort the owner runs: only claims nothing else can verify go to it, as one-line batches the owner pastes in and returns. Claude never types into OpenEvidence and never cites it (DECISIONS 2026-10-20).
  - AMBOSS, OpenEvidence and the handbook are never named or cited in the app or in card content and sources.
  - **Pregnancy and lactation guidance comes from LactMed** (NLM; owner, 2026-10-24), cited as its own source; check the FDA label for pregnancy-specific warnings.
  - **Card text is written for the reader** (owner, 2026-10-24). Never refer to the writing process, "the guidance", "the guideline names…", the review or any internal thought. State the clinical fact and cite the source with its marker.
  - Summarize, never copy. Every card gets the internal accuracy check, with extra care for doses; the review log notes how each claim and dose was verified. **The independent reviewer is deferred** (owner, 2026-10-21): cards go live without it, are listed in STATUS "Not yet independently reviewed", and get one later review pass (guideline search once; dose-heavy cards first). Never describe a card as independently reviewed until that pass is done.
- Copyrighted reference material (the reference handbook PDF in `~/Documents/Wards-reference/`) never goes into the repo.
- All content edits happen through Claude in chat; there is no in-app editing.
- Use precise medical terminology (hypoxemia, not "low oxygen"); lay terms and abbreviations only as search aliases.

## Stack
React + TypeScript + Vite, Vite PWA plugin (fully offline, prompt-to-update), GitHub Actions (checks on PRs, publish `main` to Pages), Dependabot. Content as files in the repo. Follows the iPhone's Text Size and light/dark appearance. Hidden from search engines by the page's `noindex` tag, and limited to its own scripts by a security policy in `index.html`. How to run it: see README.

## Design
- Use the AKG Design System: https://claude.ai/artifact/GWFUZ6rCthpEuhMik4Jiru (read its `project/README.md` first). Don't invent colors, type sizes or components outside it; propose additions to the design system instead.
- The app uses a copy in `vendor/akg/`; `vendor/akg/VERSION.md` says which version and how to update it. `npm run tokens` turns its tokens into `src/design/tokens.css` (iOS text styles in rem so they follow Text Size).
- Current version: Button `choice` variant with `selected` and `block` (2026-10-21, pathway decisions), after Figure drawings with a full-screen scroll-and-zoom view (2026-10-21) and Button `subtitle`, the `tinted-label` token and the `checkmark`, `plus` and `minus` icons (2026-10-20); exact version in `vendor/akg/VERSION.md`. Every symbol comes from SF Symbols (drawn after it; the README's Iconography rules). Four themes (`ios-light`, `ios-dark`, `macos-light`, `macos-dark`, set by `data-theme` on `<html>`), 43 text styles, and the React components under `AKG`, including content components (Callout, SourcePill with practice/verified markers, ContentSection + SectionBar, Flowchart, TappableValue, Table, Figure, Panel, GradeList, ScaleBar) and app pieces (Banner, BottomBar, Highlight, ShareButton, NumberField). Its README's "One color, one job" rule sets what each color means in card content. iOS component text follows Text Size via `--akg-text-unit`. The README's "Choosing controls by platform" table says which to use where.
- **Every visual element and interaction is checked against the design system and Apple's HIG** before it ships (rule summaries: `~/Documents/Wards-reference/hig/digest/`, full text alongside). Every design review asks two things: does it follow the design system and HIG, and does it look good? Icons are always drawn after an SF Symbol. When Wards needs something the design system lacks, add it there first (kept generic), then copy it in.
- The design system is shared across AKG projects. Change it only when the owner asks, and keep it generic (nothing Wards-specific).
